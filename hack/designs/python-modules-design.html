Design: Dagger modules for Python

Written in ASD-STE100 Simplified Technical English

This document tells you how the Python tools divide into Dagger modules, and why they divide that way.

1. The problem

Go has one module, because Go has one toolchain from one supplier. Python is different. Python has many tools from many suppliers. Each tool has its own release dates and its own configuration.

Two modules are live today: dagger/ruff and dagger/pytest. Both find Python projects, but each one does it differently. A third module makes a third method. This causes three problems:

  • Each module has a different opinion about the location of a Python project.
  • You must set do not check examples/ one time for each module.
  • Each module builds its own container, so no module shares the work.

2. Rules for the design

RuleReason
One tool, one module.Each tool has its own release dates and its own options. You install only the tools you need.
The shared library has no check functions.Two modules with a check for the same tool cause two runs of that tool. We saw this problem in a test.
Each tool keeps its own marker files. The library keeps the policy.A ruff.toml directory is a ruff project. It is not a pytest project. The difference is correct.
Do not put a Python environment where the tool does not need one.Ruff needs no Python. An environment makes ruff slow and gives no result.

3. Which tools need a Python environment

This is the most important division. It is not Python tool against other tool. It is the tool must see the installed packages against the tool reads only the source text.

The test used one file. The file imports attrs and has one true error (p.x + "oops").

Result. If mypy or ty do not see the packages, they report false errors. A false error is worse than no check. But ruff gives the same result with no Python at all.

4. The two layers

5. Why there is no pip module

No. There are three reasons:

  • uv pip replaces pip. We installed a requirements.txt project with uv pip install -r. The result had no pip in it.
  • pip has no verbs of its own. Every other module gives a check or a generate. There is no dagger check for pip.
  • The pip code in dagger/pytest is not for pip projects. Its resolveRunner tests the container for uv. The pip path is for a supplied container that has no uv.

Therefore pip is an install method inside env(). It is not a module.

6. Why mypy and ty are two modules

This is the weakest argument in this document. The two tools use different pattern languages for the same flag. Mypy --exclude takes a regular expression. Ty --exclude takes a glob. A directory named sdk-v1.2 needs two different escape functions. The configuration sections also differ, and ty is still before version 1.0.

The other option is one module with a typeChecker setting. The current code does this in about 15 lines. That option is legitimate. It costs less scaffolding but it hides two different tools behind one name.

7. The library interface

type Pyproject {
  # Discovery. The caller gives the markers; the library gives the policy.
  pub projects(ws: Workspace!, markers: [String!]!): [PythonProject!]!
  pub project(ws: Workspace!, path: String!, findUp: Boolean!): PythonProject!
}

type PythonProject {
  pub path: String!
  pub source(ws: Workspace!): Directory!      # include, exclude, nested projects
  pub nestedProjects(ws: Workspace!): [String!]!
  pub selected(patterns: [String!]!): Boolean!
  pub toolVersion(ws: Workspace!, tool: String!): String   # uv.lock, required-version
  pub env(ws: Workspace!, with: [String!]!): Container!    # source and dependencies
}

The with argument is important. dagger/pytest installs pytest_otel after uv sync. Installing after the sync caused dependency conflicts that nothing caught. The library must resolve the extra packages in the same pass.

The failure-report problem, in detail

The modules run the projects in parallel. This part is correct. Three tests of 6 seconds each took 6.8 seconds.

But the modules merge the results into one directory and then call sync. The first error stops all the reports. You repair one project, run again, and find the next one.

We tested the obvious repair. It collects the exit codes with expect: ReturnType.ANY. It reports all three failures, but it loses the parallel run:

MethodReportsTime (3 × 6 s)
reduce and sync (now)1 of 36.8 s
Collect the exit codes3 of 319.6 s
Both methods together3 of 323.7 s — it did not work

Dang has no structured concurrency. The Python SDK has anyio.create_task_group(), which gets both results. Dang needs the same thing. Do not repair this one module at a time.

9. Decisions against

Do not do thisReason
Do not make dagger/pip.uv pip does the work. pip has no verbs.
Do not run ruff through uv.Ruff gives the same result with no Python. An environment only makes it slow.
Do not make one large dagger/python toolchain now.It must follow four suppliers, and no part of it can be taken on its own.
Do not give the library check functions.Two checks then run the same tool. We saw this with python:test-all and pytest:test-all.
Do not make a fixed marker list in the library.Ruff and pytest have different, correct opinions about a project.

The measurements in this document are wall-clock times from dagger check on a live engine.
