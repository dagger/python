Design: Dagger modules for Python

Draft · 2026-08-28 · Written in ASD-STE100 Simplified Technical English

This document tells you how to divide the Python tools into Dagger modules. It also tells you which repositories to make. Each statement below has a test result or a source.

1. The problem

Go has one module, because Go has one toolchain from one supplier. Python is different. Python has many tools from many suppliers. Each tool has its own release dates and its own configuration.

Two modules are live today: dagger/ruff and dagger/pytest. Both find Python projects, but each one does it differently. A third module makes a third method. This causes three problems:

  • Each module has a different opinion about the location of a Python project.
  • You must set do not check examples/ one time for each module.
  • Each module builds its own container, so no module shares the work.

2. Rules for the design

RuleReason
One tool, one module.Each tool has its own release dates and its own options. A user can install only the tools that the user needs.
The shared library has no check functions.Two modules with a check for the same tool cause two runs of that tool. We saw this problem in a test.
Each tool keeps its own marker files. The library keeps the policy.A ruff.toml directory is a ruff project. It is not a pytest project. The difference is correct.
Do not put a Python environment where the tool does not need one.Ruff needs no Python. An environment makes ruff slow and gives no result.

3. Which tools need a Python environment

This is the most important division. It is not Python tool against other tool. It is the tool must see the installed packages against the tool reads only the source text.

The test used one file. The file imports attrs and has one true error (p.x + "oops").

Result. If mypy or ty do not see the packages, they report false errors. A false error is worse than no check. But ruff gives the same result with no Python at all.

5. The repositories to make

Make one repository, not five. Put one module in each directory. A user can install one module from a subdirectory. We tested this method:

$ dagger install github.com/typesafe-ai/daggerverse/deptry
Installed module "deptry" in /tmp/subpath/dagger.toml

Proposed layout

github.com/dagger/python
├── pyproject/     the shared library. No checks.
├── uv/            uv lock, uv build, uv audit
├── mypy/          type check with mypy
├── ty/            type check with ty
└── .dagger/       one set of end-to-end tests for all modules

The user installs only what the user needs:

dagger install github.com/dagger/ruff                 # lint, format
dagger install github.com/dagger/pytest               # tests
dagger install github.com/dagger/python/uv            # lock, build, audit
dagger install github.com/dagger/python/mypy          # types

Why one repository

PointOne repositoryFive repositories
Library versionAlways correct. The library and its users change together.Five pins to move for each library change.
A library faultOne commit repairs all modules.Five releases, in the correct order.
Test fixturesOne testdata/ tree for all modules.One copy in each repository.
CI and releaseOne of each.Five of each.
User installThe same. One module at a time.The same.
PrecedentNew for the dagger organization.Same as dagger/go, ruff, pytest.

Keep dagger/ruff and dagger/pytest where they are now. Users have them already. Let them use the published library. Move them later only if there is a good reason.

Note on the name. The library is not a toolchain, but dagger/go is a toolchain. Do not make dagger/python a toolchain now. Solomon said: we can always add a higher-level wrapper on top if we want later. The repository name keeps that door open.

Do we need dagger/pip?

No. There are three reasons:

  • uv pip replaces pip. We installed a requirements.txt project with uv pip install -r. The result had no pip in it.
  • pip has no verbs of its own. Every other module gives a check or a generate. There is no dagger check for pip.
  • The pip code in dagger/pytest is not for pip projects. Its resolveRunner tests the container for uv. The pip path is for a container that the user supplies without uv.

Therefore pip is an install method inside env(). It is not a module.

Do mypy and ty need two modules?

Yes, but this is the weakest recommendation in this document. The two tools use different pattern languages for the same flag. Mypy --exclude takes a regular expression. Ty --exclude takes a glob. A directory named sdk-v1.2 needs two different escape functions. The configuration sections also differ, and ty is still before version 1.0.

The other option is one module with a typeChecker setting. The current code does this in about 15 lines. That option is legitimate. It costs less scaffolding but it hides two different tools behind one name.

6. The library interface

type Pyproject {
  # Discovery. The caller gives the markers; the library gives the policy.
  pub projects(ws: Workspace!, markers: [String!]!): [PythonProject!]!
  pub project(ws: Workspace!, path: String!, findUp: Boolean!): PythonProject!
}

type PythonProject {
  pub path: String!
  pub source(ws: Workspace!): Directory!      # include, exclude, nested projects
  pub nestedProjects(ws: Workspace!): [String!]!
  pub selected(patterns: [String!]!): Boolean!
  pub toolVersion(ws: Workspace!, tool: String!): String   # uv.lock, required-version
  pub env(ws: Workspace!, with: [String!]!): Container!    # source and dependencies
}

The with argument is important. dagger/pytest installs pytest_otel after uv sync. This caused dependency conflicts for a user. The library must resolve the extra packages in the same pass.

7. Known problems

ProblemStatusWhat to do

Tool versions float. uv run --with mypy gives the newest mypy on that day. Repair Read the version from uv.lock, then from required-version, then use a default.
UV_COMPILE_BYTECODE gives unstable .pyc files. Watch The new code does not set it. If env() sets it, the container is not stable and the cache is of no use.
pytest_otel is not on PyPI. Known Publish it. Then env(with:) can resolve it with the other packages.

The failure-report problem, in detail

The modules run the projects in parallel. This part is correct. Three tests of 6 seconds each took 6.8 seconds.

But the modules merge the results into one directory and then call sync. The first error stops all the reports. You repair one project, run again, and find the next one.

We tested the obvious repair. It collects the exit codes with expect: ReturnType.ANY. It reports all three failures, but it loses the parallel run:

MethodReportsTime (3 × 6 s)
reduce and sync (now)1 of 36.8 s
Collect the exit codes3 of 319.6 s
Both methods together3 of 323.7 s — it did not work

Dang has no structured concurrency. The Python SDK has anyio.create_task_group(), and the deptry module of typesafe-ai uses it to get both results. Dang needs the same thing. Do not repair this one module at a time.

8. The plan, in three stages

  1. Make the library and prove it

    Make github.com/dagger/python with the pyproject/ module. Put in discovery, selection, source policy and version detection. Do not put in env() yet.

    Then move dagger/ruff and dagger/pytest onto it. Two users prove the interface. This also repairs the two known faults: the different exclude lists, and the pytest:test-all exit code 5 on a project with no tests.

  2. Add the tool modules

    Add uv/, mypy/ and ty/ to the same repository. Take the code from the module that is ready now. Add uv audit, because no module gives a security check today.

  3. Add the environment

    Add env() to the library. Remove the environment code from dagger/pytest. Then mypy and ty become very small: one base image and one command.

    All three tools then build the same container. Dagger gives it one address, so one uv sync serves three checks.

9. Decisions against

Do not do thisReason
Do not make dagger/pip.uv pip does the work. pip has no verbs.
Do not run ruff through uv.Ruff gives the same result with no Python. An environment only makes it slow.
Do not make one large dagger/python toolchain now.It must follow four suppliers. A user cannot take only one part of it.
Do not give the library check functions.Two checks then run the same tool. We saw this with python:test-all and pytest:test-all.
Do not make a fixed marker list in the library.Ruff and pytest have different, correct opinions about a project.
